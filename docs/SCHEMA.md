# RelayX Schema And Evidence Contracts

RelayX keeps a versioned contract for the artifacts that teams exchange between
assessment, calibration, execution, reporting, and defensive ingestion.

## Commands

```bash
relayx schema list
relayx schema list -f json
relayx schema validate result.json
relayx schema validate -k lab-profile fixtures/lab_profiles
relayx lab-matrix -f json -o lab-matrix.json
relayx lab-verify -c fixtures/lab_corpus -f json -o lab-verify.json
relayx lab-provenance -c fixtures/lab_corpus -f json -o lab-provenance.json
relayx schema validate -k lab-provenance lab-provenance.json
relayx lab-stability -c fixtures/lab_corpus -m 2 -f json -o lab-stability.json
relayx lab-diff -c fixtures/lab_corpus -m 2 -f json -o lab-diff.json
relayx schema validate -k lab-differential lab-diff.json
relayx evidence-report -r result.json -f json -o evidence-report.json
relayx schema validate -k evidence-report evidence-report.json
relayx schema validate -k module-manifest fixtures/execution_modules
relayx schema validate -k opsec-policy fixtures/opsec_policies
relayx routes -s examples/sources.json -t examples/targets.txt -f json -o relayx-routes.json
relayx schema validate -k route-report relayx-routes.json
relayx schema validate -k opengraph relayx-opengraph.json
relayx schema validate -k jsonl relayx-events.jsonl
relayx schema validate -k csv relayx.csv
relayx bundle -r result.json -d relayx-bundle
relayx schema validate -k bundle-manifest relayx-bundle/manifest.json
relayx quality-gate -C . -f json -o relayx-quality-gate.json
relayx schema validate -k quality-gate relayx-quality-gate.json
```

Invalid artifacts return exit code `2` and include path-level issue details.
Machine-readable validation reports use `--format json`.

## Artifact Kinds

- `result`: primary RelayX assessment result with `metadata`, `findings`,
  `paths`, and `sources`.
- `evidence`: atomic evidence record used by findings, paths, calibration, and
  execution annotations.
- `lab-profile`: offline calibration profile for known lab policy states.
- `lab-corpus`: offline signature corpus extracted from a RelayX result.
- `lab-provenance`: corpus provenance and operator review report for promotion
  readiness.
- `lab-stability`: repeat-capture lab stability report with consistency score,
  drift keys, and promotion downgrade reasons.
- `lab-differential`: lab response differential report comparing stable
  policy-state signatures.
- `evidence-report`: offline result evidence completeness report for
  finding/path records, source taxonomy, protocol judgement fields, confidence,
  and remaining uncertainty.
- `execution-record`: guarded validation or controlled execution audit record.
- `module-manifest`: JSON manifest for execution adapter capability planning.
- `opsec-policy`: OPSEC policy used by validation, execution, and source
  planning.
- `route-report`: route and pivot awareness report generated by
  `relayx routes`.
- `bundle-manifest`: enterprise handoff bundle manifest generated by
  `relayx bundle`.
- `quality-gate`: CI and release quality gate report generated by
  `relayx quality-gate`.
- `opengraph`: graph export for BloodHound/OpenGraph-style ingestion.
- `jsonl`: SIEM-friendly event stream export.
- `csv`: spreadsheet-oriented enterprise export.

## Evidence Contract

Every RelayX evidence record has:

- `type`: `observed`, `inferred`, `unsupported`, or `error`.
- `key`: stable non-empty evidence identifier.
- `value`: the observed, inferred, unsupported, or error value.
- `confidence`: `high`, `medium`, `low`, or `unknown`.
- `detail`: optional human-readable explanation.
- `raw`: optional object with protocol-specific supporting material.

RelayX does not require every protocol to expose the same raw fields. The stable
part is the evidence envelope: source type, key, value, confidence, explanation,
and optional raw support. That lets protocol oracles improve without breaking
downstream result consumers.

`relayx evidence-report` builds an `evidence-report` artifact from an existing
result. Candidate or relayable records without evidence are failures. Protocol
judgement records are expected to expose response classification, policy
inference, and remaining uncertainty; missing fields are reported as warnings
so teams can decide whether lab promotion or handoff is ready.

Evidence reports also include a source taxonomy. Each evidence item is mapped
to a category such as `wire_observation`, `policy_inference`,
`lab_calibration`, `source_model`, `route_model`, `control_mapping`,
`operator_context`, `error`, or `unsupported`, plus a judgement role such as
`observation`, `response_semantics`, `policy_inference`, or
`uncertainty_boundary`. This lets teams separate what RelayX observed on the
wire from what it inferred, modeled, calibrated, or received as operator
context.

## Lab Confidence Contract

Calibration reports, baseline comparisons, and lab verification reports include
contract-style fields beyond raw evidence:

- `confidence_contract.version`: currently `2` for lab calibration outputs.
- `evidence_sources`: stable signature keys that contributed to the decision.
- `present_discriminators` / `missing_discriminators`: profile discriminators
  available or absent in the observed signature.
- `promotion_gate`: whether the profile matched, whether the state is
  promotable, and whether a baseline differential signal exists.
- `remaining_uncertainty`: limitations that must remain visible in reports and
  generated profiles.

The lab matrix, lab verification, lab provenance, lab stability, and lab
differential outputs are planning, coverage, evidence-admission,
repeat-capture quality, and response-difference artifacts.
`lab-provenance`, `lab-stability`, and `lab-differential` have their own schema
kinds because teams may preserve those reports as promotion evidence.

`lab-provenance` separates corpus structure from judgement readiness. It records
whether a corpus is a synthetic fixture, operator-supplied capture, real lab
capture, or external lab capture; whether endpoint build and drift baseline
metadata are present; and whether capture-level review explicitly approves a
`promote` or `block` hint. Synthetic fixtures can validate schemas and
differential logic, but they are not accepted as real lab promotion evidence.

## Route And Adapter Contracts

Route-aware paths may include `route_reachable`, `route_reachability_state`,
`route_hop_count`, `route_pivot_types`, `route_risk_score`,
`route_risk_level`, and `route_noise_level`. These are inferred from source
profile metadata and are intended for ranking, review, and diffing.

Route reports may include `operation_control`, `guardrails`, and per-route
`reachability_check` records when `relayx routes --connect-check` is used.
Those records describe authorized direct TCP observations from the operator
runtime and preserve limitations so they are not confused with pivot-session
proof.

RelayX result metadata may include `operation_control`, `expected_telemetry`,
and `rollback`. These fields capture assessment rate limits, scheduling
windows, machine-clean output behavior, and operator review expectations for
active assessment work.

Execution records may include `adapter_sdk`, `adapter_lifecycle`, and
`artifacts`. The SDK contract records adapter registration, credential policy,
listener policy, support consistency, and lifecycle phases. This keeps module
manifests separate from actual executable adapter registration.

Execution records may also include `execution_contract`, which records whether
the selected module is lab-only, one-shot, fail-closed on timeout, and which
telemetry and evidence artifacts must be captured. Module manifests can declare
the same fields so lab-only adapter fixtures are reviewable before any live
adapter is registered.

## Enterprise And Release Contracts

`opengraph` records `metadata.field_contract_version`, a `mapping` object for
RelayX node and edge kinds, deterministic edge IDs, nodes, and edges. The
mapping documents entities such as `RelayXScan`, `RelayXSource`,
`RelayXPath`, and `RelayXControl`, plus relationships such as
`RelayXCandidateRelay` and `RelayXPathMitigatedBy`.

`jsonl` records one event per line. Every event has `event_type`, `event_id`,
`schema_version`, and `field_contract_version`. Path events preserve stable
judgement and routing fields such as `rule_id`, `decision`, `target_family`,
`source_capability`, `control_keys`, `route_state`, and `route_risk_level`.

`csv` uses a fixed header as the field contract. The enterprise CSV includes
record type, host/protocol/status, score/impact/confidence, source/target
context, relay calculus fields, source capability, defensive controls, route
risk, summary, blockers, fixes, remaining uncertainty, and
`field_contract_version`.

`bundle-manifest` records the artifacts written by `relayx bundle`: relative
path, format, schema kind, schema validity, error and warning counts, byte size,
and SHA256. This gives teams a stable handoff manifest for SIEM, graph, report,
and route artifacts.

`quality-gate` records local CI and release checks: package metadata, schema
catalog coverage, fixture parsing, schema fixture validation, enterprise matrix
coverage, lab matrix coverage, lab provenance checks, lab stability checks, lab
differential checks, documentation coverage, and GitHub workflow presence.
Failed gates return exit code `2`.

## Versioning

Current schema version: `1`.

New RelayX result files include `metadata.schema_version`. Older compatible
results that do not declare the field validate with a warning rather than an
error.
